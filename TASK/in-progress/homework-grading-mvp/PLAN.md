# 任务方案：学生作业批改系统 V1.0.0 MVP 网页应用

## 关键挑战诊断

**D-01**：挑战不是"写一个网页"，而是：设计文档只完成了"业务流程与数据模型"两块（F-01/F-04/F-05），而"技术架构与 API 契约"两块为空文件（F-02），同时系统强依赖一个文档未描述协议细节的外部中转平台（U-01/U-02）。障碍机制：若不先打通 ZenMux 调用协议与模型可用性，UI/数据库写得再多也无法产生一次真实批改，验收（端到端出图）必然失败；若先做全量界面再接 API，返工成本会集中在最不确定的接口层。因此关键路径 = 先以最小代码加真实调用验证外部依赖，再分层构建，并让三表状态机成为数据库、API、界面三层的共同语言。

**支持链**：F-02（两份关键文档为空）+ U-01/U-02（协议与模型可用性未知）+ F-04/F-05（状态机横跨三层）→ 外部依赖是链式质量链的源头弱环节。

**为何关键**：诊断直接决定行动顺序（外部依赖先行）与瓶颈判断；若诊断错误，行动顺序应完全不同。

**竞争性诊断**：
- ALT-01"挑战主要是 UI/交互体验不足"：若成立应先精做界面。证伪条件：设计文档无任何 UI 规格之外的要求（PRD 仅要求弹窗警告），MVP 验收点全部在流程正确性上——不成立。
- ALT-02"挑战主要是数据库建模"：三表结构、字段与状态机已在数据库 canvas 完整给出，照搬即可，不构成障碍——不成立。

## 指导方针

**G-01**：采用"外部依赖先行、垂直切片推进"的路线：先用最小代码加真实调用打通 ZenMux（视觉审核与生图两类调用），确认协议与模型可用后，再实现数据库层、后端 API 与前端；中转平台 SDK 代码自始独立成模块（REQ-07），其余层只经它访问外部平台。冲突取舍：界面丰富度与流程正确性冲突时，一律让位于端到端流程正确（MVP 验收点）。
- 被排除路线一："先全量 UI 后接 API"——吸引力在可见进度快，但返工风险集中在最不确定的接口层，且外部依赖未验证时 UI 验收无从谈起。
- 被排除路线二："业务代码直接调用平台 API"——实现看似更少一层，但违反 REQ-07（SDK 独立模块），且使失败排查与后续模型更换扩散到全部业务代码。
- 无真实竞争路线的事项：三表结构、状态机枚举、MVP 边界均由设计文档唯一确定，无路线取舍可言。

**优先级**：端到端流程正确 > 状态机与日志完整 > 界面完成度。

**AI 自主范围**（获批后）：在当前目录创建/修改应用文件、git init、安装运行依赖、启动本地服务验证、经环境变量使用密钥发起已授权外呼。

**必须询问条件**：需要新的外部服务凭据；需将密钥写入版本库；生成调用持续失败且排查需超出设计文档范围的变更（如更换模型或平台）。

**NG-01（不做项）**：不做用户登录/学生绑定、不校验批改结果正确性、不处理生成扭曲（REQ-10，PRD 明确豁免，避免范围膨胀稀释端到端验收）；不引入设计文档未要求的鉴权、消息队列、容器化等架构；不把审核/生图提示词存入数据库（REQ-08，保证提示词迭代不受数据迁移约束）。

## 近端目标与杠杆点

**O-01**：本轮近端目标 = 在当前目录交付可本地运行的 MVP 网页应用，完成一次真实端到端批改：上传图片 → 视觉判定通过 → 生图返回批改图片，且三表记录与日志正确。暂不追求的终局：生产部署、对象存储接入、批改教学质量优化。

**可行性**：F-03 提供密钥与模型 ID，F-07 提供运行时，Q-02 授权真实调用——首轮可达，不依赖未获得的能力。

**杠杆（L-*）**：
- L-01：ZenMux 调用层（SDK 独立模块）——一次打通即解锁视觉审核与生图两条功能路径；验证与联调资源优先集中于此。
- L-02：图片状态机（images.status）——以同一状态语义驱动数据库、API 与界面三层，减少联调歧义与返工。

**杠杆失效信号**：ZenMux 连通性验证失败且无法在设计文档范围内解决（U-01/U-02 被证伪）→ 垂直切片路线失效，停止实施，升级用户决定。

## 链式弱环节与风险

- **W-01（链首弱环节）：ZenMux 外部依赖（协议/模型可用性）**。输入=A-01 纪要与密钥；输出=两类调用的可用性证据。负责人=主程序调度、验证代理执行。进入闸门=A-02 通过后才允许 A-03+ 铺开。阻断阈值=最小调用失败且设计文档范围内无法解决。返工层=从事实层（U-01/U-02 与纪要）重查，而非在实施层盲目重试。

- **并行说明**：A-03 工程骨架与 A-04 SDK 模块骨架可并行，但整合验收（A-06）唯一对端到端负责。
